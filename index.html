Self-healing

When a fix task fails, the platform automatically spawns a remediation task. The planning phase analyzes the failure, the original steps, and the error message to produce a targeted remediation prompt — then re-queues the task. Sensitive fields (tokens, API keys) are redacted from the failure context before analysis.

Fix agents: local or cloud

When a review finding or coverage gap needs code written, a bounded agent task can do it. You pick where it runs — on your machine with direct filesystem access, or in an ephemeral cloud sandbox. Both modes share the same task queue and UI, and the result goes back through Review Bot.

💻
Local Agent Daemon

Register your machine in the UI, download the generated installer script, run it. The daemon connects to the shared Redis queue and picks up tasks assigned to your node — working directly on your local filesystem without cloning or sandboxing.

# One-time setup
node install.js # downloaded from UI
npx tsx workers/daemon/index.ts
# Node appears online in UI within seconds
  • → Works directly on your local files — no git clone
  • → Dedicated queue per node — tasks never leak to other agents
  • → REPO_MAPPINGS maps repo names to explicit local paths
  • → Heartbeat every 30 s — node shows online/offline in real time
  • → Use any local LLM (Ollama, LM Studio) to keep code on-prem
☁️
Cloud Worker (E2B)

Cloud workers run tasks in ephemeral E2B sandboxes. They clone the repository using the tenant's stored GitHub token, run the agent, commit results, and push to a new branch — without touching any local filesystem.

# Scale with PM2
pm2 start agent-worker.ts -i 3
# 3 workers share the same Redis queue
# Tasks distributed automatically
  • → Ephemeral E2B sandbox per task — fully isolated
  • → Clones repo, runs agent, pushes branch automatically
  • → Git token stored per-tenant in the database
  • → Scale horizontally — multiple workers, shared queue
  • → Can be toggled per tenant from Settings
Three-phase agent loop

Each task goes through three independent phases, each configurable with its own LLM. Use a powerful model for planning, a fast cheap model for the mechanical execution loop, and a balanced model for the final self-review.

Phase 1 — Planning

Analyzes the task, estimates complexity (low / medium / high), sets a step budget, and identifies which files to read or create. Also drives self-healing if a prior task failed.

LLM_MODEL_PLANNING=claude-opus-4-6
Phase 2 — Execution

Tool-call loop: readFile, writeFile, patchFile, runCommand. RAG queries happen here. Runs until all checks pass or the step budget is exhausted.

LLM_MODEL_EXECUTION=gpt-4o-mini
Phase 3 — Self-review

Reviews the final diff before completing. Produces a structured commit: branch name, title, body, and task summary ready to open a PR.

LLM_MODEL_REVIEW=gpt-4o

Any LLM, per phase

Reviews and fix tasks each use independently configured models. Mix providers across phases, or route everything to a local model when your data must never leave your network.

OpenAI
LLM_MODEL_PLANNING=gpt-4o
LLM_MODEL_EXECUTION=gpt-4o-mini

FAQ

How does Review Bot integrate with Jenkins? ▾
Add a Jenkins stage that POSTs to /api/review with the branch, PR URL, and mode (pr or branch). The endpoint always returns HTTP 200 so Jenkins never fails on a review error. For coverage, call /api/coverage-gate after your test run and pass the coverage-summary.json data — the bot flags files below your threshold and can trigger fix tasks to write missing tests.
How is this different from generic AI reviewers? ▾
Three ways. It runs where legacy code lives — Bitbucket, self-managed GitLab, and Jenkins pipelines, not just GitHub apps. It's grounded in your ADRs and policies via RAG, so findings cite your rules, not generic best practices. And it maintains per-repo memory of what your team adopted or rejected, filters out already-settled discussions, and feeds CI results into the review — so it doesn't drown a long-lived codebase in noise.
Can we use a local LLM to keep code off external APIs? ▾
Yes. Set LLM_BASE_URL to any OpenAI-compatible endpoint (Ollama, LM Studio, vLLM, etc.) and all phases route to your local model. Combined with an on-prem deployment and a local Qdrant instance, your code, docs, and inference can all stay within your network perimeter.
What are fix agents, and can they run on my local machine? ▾
Fix agents are bounded coding tasks that act on review output — writing tests flagged by the coverage gate or drafting a fix for a finding. They can run in cloud sandboxes or locally: register your machine in the UI, download the generated installer script, and run it. The local daemon picks up tasks assigned to your node and works directly on your filesystem. The resulting PR goes back through Review Bot.
What happens when a fix task fails? ▾
Self-healing kicks in automatically. The platform analyzes the failed steps and error message, generates a remediation prompt (with sensitive values redacted), and re-queues a fix task. You can also review the full step trace in the UI to understand exactly what went wrong.
Does RAG Chat replace the review for code questions? ▾
They complement each other. RAG Chat is for interactive questions about the codebase — fast, streaming, with cited sources. When the answer leads to "let's implement this", you can spawn a fix task directly from the chat thread. The task then has access to the same RAG context used to answer the question, and its PR is reviewed by Review Bot.
